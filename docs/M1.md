# M1 — Link and latency harness

M1 is a **measurement milestone, not a feature**. It fills in the empty table in
[ARCHITECTURE.md §6](ARCHITECTURE.md) and answers the two questions that decide
whether the rest of the design survives contact:

1. **Wi-Fi jitter under motion** — does the control link stay bounded while the
   robot is actually moving?
2. **Decode cost under Rosetta** — is the emulated bridge fast enough to keep up
   with the camera? (This is the number [DECISIONS.md](DECISIONS.md) #11 says we
   need before reconsidering native arm64.)

The no-robot smoke test is meaningful on its own: DJI's UnityBridge **loads,
initializes, runs its event loop and scans for robots** as an amd64 library under
Rosetta 2 on Apple Silicon. The transport is not theoretical.

## Build

```bash
./scripts/install-bridge.sh   # copy DJI's blob out of the Go module cache into ~/.unitybridge
./scripts/build.sh            # builds bin/s1probe as amd64 (Rosetta) — see DECISIONS.md #10
```

`install-bridge.sh` takes the library from the `brunoga/robomaster` module cache.
It is proprietary DJI code: it is never committed here and never redistributed.

## Running it

Verify the toolchain end-to-end without a robot — expect a clean
`starting client: timeout` after ~30 s:

```bash
./bin/s1probe -connect-only
```

Then, with a vehicle powered on:

```bash
# WiFi Direct: join the Mac to the S1's own AP first. Simplest for bring-up.
./bin/s1probe -wifi-direct -connect-only

# Full run, 60 s of video, JSON for the record.
./bin/s1probe -wifi-direct -video 60s -json runs/$(date +%Y%m%d-%H%M)-direct.json
```

### Flags

| Flag | Default | Meaning |
|---|---|---|
| `-wifi-direct` | off | Connect to the robot's own AP. Off means router mode (robot joined to your LAN via a QR-code-configured appID). |
| `-appid` | 0 | Router mode only. 0 connects to the first robot found. |
| `-video` | 30s | How long to sample the stream. |
| `-rtt-samples` | 30 | Control-plane round trips. |
| `-connect-only` | off | Connect, report link facts, exit. No video, no motion. |
| `-allow-chassis` | **off** | Opt in to a brief chassis nudge. See safety below. |
| `-json PATH` | — | Write the full report. |
| `-v` | off | Verbose library logging. |

### A trap worth knowing

`Chassis.SetSpeed()` returns `nil` and does nothing — the S1 ignores that key and
`DirectSendKeyValue` never acknowledges. Movement must go through
`Controller.Move` with a ~20 Hz refresh (DECISIONS.md #12). **No command from
this bridge is ever acknowledged**, so never treat a nil error as proof the robot
acted. Watch the robot.

### Safety

**The harness does not drive the robot by default.** The actuation probe rotates
the *gimbal*, which moves in place — nothing rolls off a table. Chassis motion is
opt-in via `-allow-chassis`, and even then is a 300 ms nudge.

Put the vehicle on the floor with clear space before using `-allow-chassis`.
The blaster is never touched by this harness at all.

## What it measures, and what it cannot

Measured in software:

| Series | Meaning |
|---|---|
| `control_plane_rtt_wire` | Forced `useCache=false` get. **Does not measure the link** — see the caveat below. |
| `control_plane_cached` | The cached path, kept as a control so the two can be compared. |
| `gimbal_command_issue` | Cost of issuing an actuation command through the bridge. |
| `video_inter_frame` | Frame arrival intervals. **The jitter figure is the one that matters** — a deadman fires on the worst case, not the mean. |
| `jpeg_encode` | Our own cost to prepare a frame for foveate's frame store. |
| FPS + deficit vs. nominal 30 | Measured throughput. A large deficit with pinned CPU is the signature of decode losing to emulation. |
| CPU cores busy | The Rosetta cost, quantified. |

**Not measurable in software, and the report does not pretend otherwise:**

*Control-plane RTT.* Measured 2026-09-04: even with `useCache=false` forcing the
non-cached path, gets return in 0.2 ms p50 against 0.0 ms for the cached path.
Sub-millisecond is not a Wi-Fi round trip — DJI's bridge answers from its own
internal state. The number is real but it measures the bridge, not the link.
Both series are kept in the report because the comparison is the evidence.

*True key-to-motion and glass-to-glass latency.* Those include display
pipelines and mechanical response. To get them, film the screen and the robot in
one frame at high frame rate and count frames. Worth doing once, by hand, to
calibrate how much to add to the software numbers.

## Interpreting the result

- **FPS near 30, CPU well under 1 core** → Rosetta is a non-issue; #11 stays
  deferred and we proceed to M2.
- **FPS sagging with CPU pinned near/above 1 core** → decode is losing to
  emulation. Re-open [SPIKE-arm64-bridge.md](SPIKE-arm64-bridge.md); the library
  re-platforms in one `vtool` command and only the host-process problem remains.
- **High `video_inter_frame` jitter but healthy FPS** → the link, not the CPU.
  Compare WiFi Direct against router mode before concluding anything.

Run both Wi-Fi modes. STATUS.md open question #3 is whether direct mode forces
the Mac off the network hosting Redis and Ollama — that is a real deployment
constraint, and M1 is when we find out.
